- **Evidence:** `TimeFold.swift:57–62` (interpretation 1) says the coupling target "is chosen from the **segment-start** energy band; a band crossing inside a segment takes effect at the **next** segment", and `TimeFold.swift:183` names the local `bandAtSegmentStart` — but it is computed **after** the segment's waking decline has already been applied, i.e. from the segment-**end** energy, so a crossing takes effect **in the same segment**, one segment earlier than documented.
- **Probe (material):** 2 h waking fold, mood 60, energy 46 (Relaxed at start; 43 = Drowsy at end). Shipped code couples for the whole segment → mood 47.8354 (= 60 − 25(1−e^(−2/3)), verified live). The documented segment-start reading leaves mood at 60. The suite's `couplingAndFloor` fixture (energy 10 → 8.5) is in-band under both readings, so **no shipped test discriminates which semantics is normative**.
- **Adjudication:** §4.3 does not pin intra-segment timing; both discretizations are defensible engine-owned dynamics and the coupling is self-healing, so this is **not a spec violation** — it is a documentation-integrity defect: the header pins interpretations "for review", and one of them is not what the code does. No numeric pin is wrong.
- **Required disposition (cheap, before commit):** fix the header text (and the misleading local name or add a correcting comment) to document the shipped post-decline read — or change the code to the pre-decline read; either is a few lines.
