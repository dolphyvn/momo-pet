### MAJOR-1 — The 30–90-minute "recently-fed nibble" is a new response class that contradicts FR-6's normative response assignment, and it is presented as PRD-delegated instead of flagged
- Location: 05:320 (§4.4 effect table row "Feed (recently-fed nibble) | effects × 0.25"), 05:329–335 (§4.5 table: Recently fed → "Small contented nibble (shortened eating animation)", × 0.25), 05:329 + 05:26 (framing: "PRD §4 delegates the value, 04 §9.2 delegates the window to the engine" / §0 #7 "engine-owned tunable, PRD-delegated"), `ADR-004:18` ("Satiety window (PRD-delegated decision)").
- Evidence: FR-6 (`02:269`): "Response is state-gated per §4: hungry → enjoys meal (mood+, energy+); **recently fed → politely full, zero penalty**." The §4 matrix (`02:164–170`) has one fed column — "Just fed (full)" → "Politely full — cute refusal, zero penalty" (`02:167`) — and the delegated open item is only the **window value** (`TASK-006:48`: "satiety window value (open — TASK-006 decides)"). Once the engine defines hungry as > 90 min, FR-6's "recently fed" spans 0–90 min, and its normative response for that entire span is the politely-full refusal with zero state change. The architecture instead splits that span: 0–30 keeps the PRD response, 30–90 gets a shortened eating animation with ×0.25 state effects — a third response class the PRD does not contain. Unlike this document's two other letter-vs-design divergences (interpretation I-1 at 05:307, the §5.5 box at 05:392), this one is flagged nowhere: §4.5, §0, and ADR-004 all assert the delegation framing. The underlying tension is real and worth resolving deliberately — 04 §9.2's `SatietyHint` has three values (.hungry/.recentlyFed/.full), which structurally implies three distinguishable character states while FR-6's letter describes two response classes — which is exactly why it required a flag, not a silent resolution.
- Why it matters: ResponsePlan-per-PRD-§4-matrix is a binding intake obligation, and the matrix is normative. An unflagged deviation enshrines a product-semantics change (new response class; nonzero state effects for a state FR-6 assigns zero effects) without owner or PRD sanction — the precise failure mode the document's own flagging discipline (and CLAUDE.md §25's honesty rules) exists to prevent.
- Correction: Handle exactly like §4.8's box. Either (a) conform to the letter — 30–90 min = the politely-full refusal, with `SatietyHint`'s three values still distinguishing the character's resting rendering; or (b) keep the nibble but record it as interpretation I-2 / OPEN-5 with a PRD-fix-candidate note on FR-6's wording and a flip-ready response-matrix test, and correct the framing in §4.5/§0/ADR-004 to "the window value is PRD-delegated; the response class is PRD-owned — this document proposes the nibble class for owner confirmation." Either is a documentation-level fix; (b) is likely the product-right answer, but it must be surfaced, not silent.

### MAJOR-2 — The sync guards have unspecified reset semantics: a Watch-side counter reset starves every later pat forever, and the "app reinstall" sync edges are absent
- Location: 05:497 (`IntentEvent.watchSeq` — "monotonic per-Watch counter"), 05:512–513 (§6.4: apply iff "intent UUID is unseen … **and** `watchSeq > lastAppliedIntentSeq`"; prune journal ≤ watermark), 05:492 (watermark inside the snapshot), 05:522–529 (§6.6 table — no re-pair/new-Watch row, no iPhone-reinstall row), 05:640 (§11.3 notes unpairing "wipes Watch-local data at the system level" without connecting it to the watermark), 05:690–695 (OPEN/VERIFY register — the case is unregistered).
- Evidence: The `watchSeq` counter must persist across Watch app launches (else the watermark would starve every relaunch), so it lives in the Watch store — which watch-app deletion and unpair/re-pair erase (the document itself states unpairing wipes Watch-local data, 05:640; a new Watch is fresh). After such a reset, the first new pat carries watchSeq = 1 while the iPhone's `lastAppliedIntentSeq` keeps the old device's high-water mark (say 50): `1 > 50` is false, the intent is not applied, the watermark never advances, and **every subsequent Watch pat is silently dropped** — no counters, no Q7 ticks, no hello — with no error surface by design (05:518). That is FR-18 AC-1/AC-2 broken by the spec's letter in a mainstream lifecycle (new or re-paired Watch). The sibling case: iPhone app deleted + reinstalled while a paired Watch holds a stale snapshot and an un-drained journal — a fresh store has an empty UUID set and watermark 0, so pre-erase pats replay into the new pet (including a phantom hello +8; system retention of undelivered transfers across reinstall — VERIFY-AT-BUILD) and the stale old-name snapshot renders until the first push; and an intent whose `dayKey` has no ledger entry (pruned by the 7-day retention, or pre-dating a fresh pet) has no specified create/drop rule. The review brief explicitly lists "app reinstalls" among the sync edges to cover; §6.6 and §10.4 cover neither.
- Why it matters: The dual-guard mechanism itself is sound for replay/duplicate/restore (§6.4's headline cases all check out); the defect is that neither guard's **reset** semantics exist, so the ordinary device-lifecycle events fall outside the contract, and one of them degrades the product's core Watch interaction permanently and invisibly.
- Correction: Specify guard reset semantics — e.g., `IntentEvent` carries a per-install `watchSessionEpoch` and the iPhone stores the watermark per epoch, or the iPhone resets `lastAppliedIntentSeq` when a WCSession activation reports a fresh journal — one mechanism, written into §6.2/§6.4. Add §6.6 rows for "Watch re-paired / watch app reinstalled / new Watch" and "iPhone reinstalled with paired Watch", a §10.4 test row (counter reset, then pat applies exactly once), and the expired-dayKey rule (recommend: apply current-state effects, drop day-ledger attribution for pruned or pre-install days, never resurrect days; document stale-journal absorption on fresh install as the intended warm behavior). Mark the system-dependent WC queue behaviors VERIFY-AT-BUILD.

### MINOR-1 — Window checks do not specify their reference time for delayed (offline-queued) intents
- Location: 05:381 ("Window checks at completion time: Q1 ticks only if local time < 12:00; Q6 only inside 20:00–07:00; attribution always to the intent's `dayKey`").
- Evidence: For an 11:30 Watch pat applied at 12:30 (the exact offline-journal path §6.4 normalizes), "local time < 12:00" is ambiguous: the intent's own timestamp ticks Q1; the application instant does not. The document already commits to event-time semantics for attribution (05:512's 23:30 pat; D20 day-ownership at 05:381's own third clause) — but a literal implementer can read "completion time" as apply-time, and the two implementations diverge on a reachable case.
- Correction: One sentence: window checks evaluate the interaction's **local timestamp** (consistent with `dayKey` attribution), not the application instant.

### MINOR-2 — Interaction semantics during `.waking` are undecided
- Location: 05:356–366 (§4.7 transition diagram: waking "never cancelled — completes on return"; no interaction rule for the waking stretch), 05:303–312 (§4.4 covers bands + satiety + settling, not waking).
- Evidence: The intake confirmed settling interactions (decline-warm, 05:372) but 04 §9.6 item 8's open question — "which interactions queue until wake vs. decline-warm" — also had a waking half: 04's transitional-wakefulness note proposes queue-until-wake for waking, left for TASK-006 to confirm. The architecture confirms neither. A feed or play arriving during the 1.8–2.5 s waking stretch has no defined ResponsePlan, yet D18 requires every interaction to get a warm response and the §10.3 response-matrix table test needs the cell defined.
- Correction: One sentence in §4.7: confirm queue-until-wake, or (recommended, symmetric with settling and simpler — waking is ≤ 2.5 s) decline-warm with the post-wake state's response. Either way the engine contract must be total over `.waking`.

### MINOR-3 — The character-facing read-model (04 §9.2's `CharacterDisplayState`) has no placed derivation; DisplayState is declared "the one derivation"
- Location: 05:408 ("DisplayState read-model (**the one derivation** behind every surface)"), 05:413–426 (DisplayState fields; "the Watch snapshot (§6) carries exactly this shape").
- Evidence: 04 §9.2's engine→character contract feeds the character a `CharacterDisplayState` carrying `moodBand`, `energyBand`, `activity`, `satietyHint`, `wakefulness`, `momentRequest` — fields DisplayState does not have (it carries words/keys, bondStage, questLine, greeting). ### MINOR-4 — D-R1's enforcement claim is overstated: a macOS build does not catch an accidental SwiftUI import
- Location: 05:121 (D-R1 enforcement: "compiles and unit-tests on macOS via `swift test` — an accidental UI import fails the macOS build. This is the project's purity guarantee"), `ADR-005:11` (same claim).
- Evidence: SwiftUI exists on macOS, so `import SwiftUI` in MomoCore compiles and `swift test` passes; the mechanism catches only platform-locked imports (UIKit, WatchConnectivity, HealthKit). ## Verdict Evidence

The review attempted to disprove the document on every axis in the brief, and the architecture held nearly all of them under real pressure: the purity story is structural rather than asserted; the engine consumes the 04 §9 contract faithfully, including both confirms the intake demanded, the full cancellation vocabulary, and the single-instant play rule; the bond, quest-generation, seed, and cascade machinery all survive arithmetic and letter checks against the normative PRD; the sync design's core cases (replay, duplicates, offline attribution, day-ownership, conflict dissolution) all check out; VERIFY-AT-BUILD discipline is genuinely comprehensive rather than decorative; the privacy, testing, and performance sections are complete and concrete; and the document's flagging discipline is applied twice where it mattered most. What blocks commit is two concrete defects, both in the same class the document elsewhere handles well — unflagged divergence from normative text, and unspecification at lifecycle edges. MAJOR-1 introduces a feed response class FR-6 assigns differently and labels it PRD-delegated when only the window value was delegated; MAJOR-2 leaves the sync guards' reset semantics unspecified, so a new or re-paired Watch silently and permanently stops counting pats, and the in-scope reinstall edges are absent from §6.6/§10.4. Each has a small, local, well-defined fix; neither requires restructuring; the four MINORs are one-or-two-sentence specifications each.
