## 1. Spec derivation (normative behavior established BEFORE reading the code)

From 05 §6.1–§6.6 and ADR-003/ADR-013, the reviewer independently derived the following expectations, which the implementation must satisfy:

1. **Push leg (iPhone→Watch)** — `updateApplicationContext`, latest-wins, coalesced: every push carries the FULL state (display, questInputs, haptics, watermark pair), never a delta; the counterpart is guaranteed only the newest value, so anything that must eventually arrive (the §6.6 reset marker) must ride EVERY context until consumed. The push happens on the plan's `.pushWatchSnapshot` step, IFF-changed, in the plan's fixed step order (persist → response → moments → push).
2. **Receive leg (Watch→iPhone)** — `transferUserInfo`, FIFO contract stream. §6.4's dual idempotency guard: apply iff (a) the intent UUID is unseen (the engine's `processedIntents` belt is the ONLY UUID memory — no second seen-set store may be invented) AND (b) `watchSeq > lastAppliedIntentSeq` for that intent's epoch, with per-epoch watermarks 0-initialized on first sight of an epoch. Strict `>`; accessor-driven (the call site names `SyncState.shouldApply` or a plan core that does, never a raw gate with call-site watermarks — O5).
3. **Record-before-apply + propagation (the F-1 shape)** — the watermark pair recorded from an apply must be what the NEXT snapshot builds from; a wiring leg green decision tests cannot see. Duplicates/replays/redeliveries/stale-seq are FULL no-ops: no engine apply, no sync-state write, no push (INV-10). Exactly-once under FIFO, at-most-once under seeded shuffles (O2 — strengthening the shuffle pin would pin a falsehood).
4. **Reset marker (§6.6)** — erase writes a reset marker that rides EVERY context from the erase until Watch consumption (TASK-041/044). It must survive the erase (the store tree is deleted) and at least one relaunch, so it needs its own persistence OUTSIDE the erased tree. Schema evolution must be adjudicated: both DTO decoders gate `schemaVersion ==` strictly, so a bump drops whole payloads at every pre-bump decoder and fires the OBS-3 parity-fixture obligation; the additive-OPTIONAL field (`decodeIfPresent`/`encodeIfPresent`) evolves with no bump and is the smaller shape.
5. **O1 one-writer** — each persisted sync file (journal, sync state) has exactly ONE production write path on the executor's single dispatch path. **OBS-1** — the launch read is the single sanctioned synchronous main-thread I/O; the receive hot path must be I/O-free beyond the off-main persist handoff.
6. **Placement (ADR-013)** — WC wrapper/protocol/live-session code is app-target code duplicated per target; pure decision logic in MomoKit; no app-to-app target dependency (D-R3: `dependencies = ()` for both app targets).
7. **Transport facts the design may assume** — VERIFY-AT-BUILD: these must be resolved against real SDK evidence, not memory, with honest §25 scope notes about what runtime proof remains (TASK-044, paired hardware).

Everything below checks the implementation against THESE derivations.

## 5. Findings

**F-1 · HIGH · The reset marker's launch-load site and erase-save site read/write different directories — the marker never survives a relaunch in the wired app.**
- *Evidence*: Save: `Apps/Momo/MomoAppModel+Settings.swift:100` (`markerDirectory = try StoreRules.watchResetMarkerDirectory()`), `:106-108` (store + save) → `Application Support/watch-reset-marker.json` (StoreRules.swift:141-143 = `defaultDirectory().deletingLastPathComponent()`; `defaultDirectory()` = `Application Support/Momo/`, StoreRules.swift:162-170). Load: `Apps/Momo/MomoAppModel.swift:383-384` — `WatchResetMarkerStore(directory: directory)` where `directory` is the executor's STORE TREE (`Application Support/Momo/`) → `Application Support/Momo/watch-reset-marker.json`. The two paths can never meet.
- *Concern*: erase → relaunch → `watchResetMarkerEraseCount` initializes to 0 → every subsequent context omits the marker → the Watch (TASK-041) never consumes a wipe → stale pre-erase journal entries drain over the FIFO stream and apply warm onto the fresh pet. This is EXACTLY the §6.6 hazard D-2 identifies as the reason the marker exists ("a lost marker means a fresh 0-init watermark, which ADMITS stale pre-erase journal entries"), reintroduced one layer up, in the executor wiring. AC-4's "the marker survives erase + relaunch (pinned)" is violated in the wiring while passing at store level (`WatchResetMarkerTests.markerOutlivesTheErasedStoreTree` saves and loads through the SAME directory, so it is structurally incapable of seeing the divergence — the TASK-034 F-1 blind-spot shape the contract explicitly warned about). Probe C proves the suite cannot catch even a deliberately broken load directory.
- *Suggested fix*: the launch load must use the same derivation the erase path uses — `try StoreRules.watchResetMarkerDirectory()` (with the same DEBUG-loud + throwaway-fallback discipline +Settings.swift:100 applies) — plus a pin that the load site and the save site derive from the same rule (extend guard 3 to scan the init's marker-load directory token, or add the behavioral pin once an app-target test seam exists).

**F-2 · MEDIUM · The test gap that let F-1 through: no test reaches the executor's launch-load site.** Guard 3 pins only the save-before-delete ordering inside `+Settings.swift` text; the marker suite exercises the store in a single directory; nothing constrains what directory `MomoAppModel` init loads from. Fixing F-1's code without closing this gap leaves the divergence class open (the same-task sync-state load at MomoAppModel.swift:387 is consistent with its persist path — verified — but is consistent only by luck of convention, not by pin). *Suggested fix*: the guard/pin named in F-1; treat F-1 and F-2 as one fix unit.

**F-3 · LOW · Release-build marker-save failure is silent (D-3).** A failed marker save followed by the store-tree deletion loses the wipe instruction with no retry, and (pre-fix) nothing would resurrect it. House posture already accepts DEBUG-loud for store failures, a new `watchSessionEpoch` eventually invalidates the stale journal by watermark rule, and the next push attempts the marker again only after another erase — acceptable for MVP, but worth a follow-up note in TASK-041/044's consumption design (the Watch could also self-defend by validating its journal's epoch against the incoming snapshot's).

**F-4 · note · Best-effort durability of the spent snapshotSeq (D-5).** A crash between context send and the async actor persist can rewind `nextSnapshotSeq` once across relaunch; consequence is display-level (seq consumption is monotonic bookkeeping, not exactly-once authority — the watermark+belt pair owns that). Correctly documented in code; no action.

**F-5 · note · `watchSyncEpoch` advertisement can transiently revert.** A late old-epoch event applying after a newer-epoch event sets the advertised epoch back until the next new-epoch apply; effect is delayed pruning only (max-semantics watermarks are per-epoch and unaffected). Inert; no action.

**F-6 · note · D-7 accepted as disclosed.** No app-target test target exists, so the executor arm is covered structurally + by the kit-level F-1 loop pin. Acceptable now; the protocol seam is the right investment; revisit if TASK-041/042 lands without a Watch-side harness either.

**F-7 · note · D-12 correctly deferred.** The stale "reserved no-op" doc comments in `AppModelPlan.swift` are now inaccurate; contract-frozen content, doc-only follow-up for the orchestrator.

**F-8 · note · MomoAppModel.swift at exactly 800/800.** Zero headroom; every further executor change must land in extension files (the `+Watch` pattern). Flag for orchestrator awareness only.
