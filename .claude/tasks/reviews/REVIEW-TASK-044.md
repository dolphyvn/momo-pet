## Phase-1 derived spec (the review's measuring stick)

- **§10.4 rows (7)**: iPhone→Watch (codec versioning + latest-wins re-render); Watch→iPhone (offline pat exactly-once; AC-2 same counters/quests; UX-6 hello idempotency); Temporary disconnection (**journal drain on reconnect**; last-snapshot display with zero UI acknowledgment); Stale data (sane cascade, no error surfaces); Conflict (replay/duplicate no-ops, INV-10; bond non-regression AC-4); Guard reset (0-init watermark applies new-epoch pats exactly once; stale-epoch watermark never prunes the new journal; the erase → marker → wipe chain); Termination/relaunch (Watch restore ≤ ~2 s; iPhone relaunch ≤ 1 s; **WC frame delivery under suspension = device obligation**).
- **R1 hazards derived before reading the code**: the sweep must never resurrect pre-reset journal entries — after an erase the iPhone store is fresh (empty UUID set, watermark 0), so a pre-wipe entry reaching the wire applies warm onto the new pet. The WC serial queue emits `activationDidCompleteWith` BEFORE the pending context (the §6.1 VERIFY-AT-BUILD launch-delivery record), so a literal drain-at-activation structurally cannot satisfy the contract's own "pending marker ⇒ zero send" rule; the launch legs must order consumption ahead of any drain, and the drain's journal read must be revalidated against post-wipe state (count-recheck or equivalent). Flush triggers must be enumerable; the sweep must be verbatim (no re-stamping), journal-preserving on send (the watermark prune owns removal, INV-10 cited not re-derived), O1-clean (one-writer seam), timer-free, and one-shot per activation.
- **R2**: the seam must route REAL bytes through the production `receiveContext` with `WatchResetConsumption.decide` unmocked, be provably release-inert (`#else` shape), and carry a control that discriminates marker-caused wipe from seed-caused render, plus a disk-durability leg.
- **R3/R4/R6**: comment-stripped, both-direction fixtures, non-vacuous real-tree runs, exactly-one-red bites; R6 must enumerate the two legitimate send legs without weakening any pre-existing pin (a forged third site fails alone).
- **Contract defects found**: none material. R1's letter ("fires at activation legs, nothing else") is satisfied in substance by arm-at-activation + flush-at-first-receive-decision; the contract's own hazard rule forbids the literal reading (drain-at-activation races the marker), so the landed design is the compliant one, and the residual liveness gap (activation with no subsequent context) is bounded, disclosed, and benign (the events are durable; the no-context case means the iPhone has never run — nothing to apply to).

## Findings

Fix: a one-word table edit at the orchestrator's closeout docs pass. Does not block.
- **F-2 (Note — accepted residual, honestly disclosed): the consume-suspension window.** The task file and code comment disclose "a consumption suspended INSIDE `consumeWipe` at the flush's read instant". Reviewer-verified precise shape: `consumeWipe` has exactly ONE internal suspension (`await WatchSnapshotStore(directory:).wipe()`, `Apps/MomoWatch/MomoWatchAppModel.swift:47`); during it the persister actor is free, and a SECOND context frame processed while frame A's consume is in flight (main-actor reentrancy across `receiveContext`'s awaits) can submit `pruneJournal`/`pendingEvents` ahead of the wipe's resume — the flush then reads PRE-wipe bytes while the model's `consumedEraseCount` is not yet advanced, so the count-recheck cannot fire, and pre-erase pats go to the wire. Receiver-side outcome: warm-apply on the fresh store — the doc-pinned semantic (§6.6 "iPhone reinstalled" row) and the same class as WC's own queue-retention exposure already on the VERIFY-AT-BUILD register. The ordinary paths are closed: the primary defense is program order (consumeWipe awaited before the flush, count updated before the flush call), the second is the count-recheck (probe-verified live), and the window requires a back-to-back-frame race inside one suspension. Disclosure is present in both the task file and `flushStrandedJournal`'s doc. Accepted.
- **F-3 (Minor — guard-strength suggestion, non-blocking): the consume-branch order pin does not pin the `await`.** `Tests/MomoKitTests/Support/WatchSweepScan.swift:136` requires `persister.consumeWipe(` before the flush site but not the token `await persister.consumeWipe(`; a future revert to `Task { await persister.consumeWipe(…) }` + immediate flush would keep this leg green while widening F-2's window from a suspension micro-race to the whole consume. The shipped code has the await (`MomoWatchAppModel.swift:401`). Recommend pinning the awaited spelling at the next guard touch (one-token tightening).

## Verdict rationale

The E2E drives the real consumption path with a discriminating control and a disk-durability leg, and its seam is release-inert by construction. The guard ride-alongs are truthful: no pre-existing pin weakened in any direction, both new censuses bite exactly-once on the real tree. All §19 gates re-run green, numbers matching the implementer's records exactly (1161/113; 90.84 %; 9/9). The findings are one record-level misattribution (F-1, a table edit at closeout) and one non-blocking guard-strength tightening (F-3, a future one-token change); the accepted residual (F-2) is real, narrow, honestly disclosed in code and task file, and of an already-pinned receiver-side class.
