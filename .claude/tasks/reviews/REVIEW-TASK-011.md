## Findings

### MAJOR
None.

### MINOR
1. **`TokenPurityTests` is hex-shaped; component/named-color initializers would evade it.** `Tests/MomoCharacterTests/TokenPurityTests.swift:23-25` scans `(?:0x|#)[0-9A-Fa-f]{6,}` only. A future `Color(red:green:blue:)`, `.foregroundStyle(.blue)`, or gradient stop outside the token module would satisfy R4's *spirit* violation while passing the scan. Today's tree is fully clean (verified by grep — zero RGB-component or named-color usages anywhere in `Sources/`+`Apps/`), so AC-2's letter and spirit currently hold; this is a hardening gap, not a violation. *Suggested fix (follow-up task, not a re-run):* extend the scan to also flag `Color(red:` / `Color(hue:` and SwiftUI named-color member accesses outside the token module, mirroring how `ImportWhitelistScan` enforces D-R1.

### NITPICK
2. **Sentinel rationale slightly overstated.** `Sources/MomoCharacter/MomoCopy.swift:83-84` claims "`localizedString` cannot return a value containing NUL". The property actually relied on is exact-equality implausibility: a real translation would have to equal the full `\0momo.copy.missing\0` sentinel to collide. Behavior is correct and unit-tested (missing key → `nil` via the production `Bundle.localizedString` path); only the comment's wording overclaims. *Fix:* reword to "a real translation equal to this sentinel is implausible by construction."
3. **Contrast ratios are recorded prose, not mechanically pinned.** The figures appear in `MomoUIColors.swift:12-16` and the task file; no test recomputes them, so a future token change could silently invalidate the comment (full audit is TASK-047 per contract, so recording-only meets the letter). *Optional hardening:* pin the four body-text pairs' ≥ 4.5:1 with a small luminance helper in `MomoDesignTokensTests`.

### Verified-benign adjudications (probed, judged compliant)
- **Two-file hex allowlist vs the task's singular "token file".** Requirement 1 defines the token *module* (`MomoCharacter`) and pre-delegates layout ("or the layout TASK-009 recorded"). The allowlist is the two palette-definition files of that module (`MomoColorToken.swift` itself contains no hex by design); the purity test pins the exact allowlist and asserts non-vacuity. Faithful to the intent (single source of truth; R4 zero-hex downstream) — not a letter violation.
- **Seed key `momo.line.moment.00` is not consumed by any view.** Requirement 4 mandates catalogs "exposing the three copy namespaces"; the scaffolding test pins all three namespaces present and the seed set at exactly 3. One key per namespace is the minimal compliant set.
- **Inert shell literals** (`Home — placeholder`, `Feeling happy`, `Wish placeholder`, `Pat`): documented in-file as placeholder anchors; catalog namespaces are for `momo.line.*` copy, not every string; none is a tone-guide line; "Pat" is TASK-004's sanctioned action label. "Feeling happy" echoes project.md §13's complication example and the §3.5 mood-word slot — a placeholder status value, not pool copy.
- **Watch glance keeps the system ground** (no background token on watchOS): deliberate and documented in the view header; watchOS owns its chrome; content tokens are all consumed and pixel-verified.
- **`_ =` existence pins** for typography in `MomoDesignTokensTests.swift:59-62`: weak but honest — existence + scale ordering is what is unit-testable; Dynamic Type correctness is a system-text-style property.
- **"Watch canvas defect" fix:** re-derived from pixels — the 32 pt strip renders at y 144–207 px on the exact 324×394 ADR-008 canvas with 15,036 exact-color pixels; the deterministic `frame(height: 32)` replacing the collapsing `aspectRatio(.fit)` shape is a sound, minimal, documented fix (in-code comment + §20 root-cause record in the task file), not a hack.
