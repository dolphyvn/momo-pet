# ADR-013 — Standalone watch app packaging

## Status
ACCEPTED — decided and shipped in TASK-009 (EPIC-002, commit `b28ccb4`, 2026-09-08; REVIEW-TASK-009 **APPROVED**, whose independent re-runs authenticated the decision's evidence). REVIEW-TASK-009 NITPICK-2 flagged that the decision then lived only in task notes and asked for ADR promotion "when EPIC-008 starts, before the companion/sync design hardens around it"; status.md carried the reservation (originally "ADR-009 candidate", renumbered **ADR-013** by the TASK-027 housekeeping). Promoted to this record 2026-09-10, before EPIC-008 begins. **Nothing new is decided here** — this ADR persists the TASK-009 decision with its full rationale. Implements 05 §2.3 D-R3's enforcement clause at the project level.

## Context
ADR-005 fixed the module map — one repo-local Swift Package (MomoCore/MomoCharacter/MomoKit) consumed by two app targets — but deliberately left the Xcode-project template specifics VERIFY-AT-BUILD at bootstrap ("ADR-005 … VERIFY-AT-BUILD for project-template details at bootstrap", 05 §2.3 rationale). TASK-009 created the real project and therefore had to fix the watch target's project-level shape. Three recorded facts framed the choice:

- **05 §2.3 D-R3** (dependency rules): "App targets never import each other; all shared state flows through MomoKit DTOs over the WC transport" — enforcement: "No target dependency between `Momo` and `MomoWatch`; review check."
- **The doc chain is silent on embedding**: TASK-009's grep of the docs found no guidance on embedded-vs-standalone watch packaging — the shape was genuinely open at project-creation time.
- **MomoWatch is an independent surface, not a remote view**: 05 §2.1's target table assigns it its own full role set (snapshot display, cascade rendering, pat capture + intent journaling, the WC Watch-side session, LOD character, AOD static glyph, haptics), and ADR-003 keeps the Watch engine-free — render the snapshot, journal the pats. The classic alternative shape (a watch app embedded inside the iOS product) is built on exactly the target dependency D-R3's enforcement clause forbids.

## Decision
**MomoWatch ships as a standalone watchOS application target — not an embedded watch app inside the iOS product:**

1. **Target shape.** `MomoWatch` is `com.apple.product-type.application` with `WKApplication = true`, and there is **no target dependency between `Momo` and `MomoWatch`** — both app targets were created with `dependencies = ()` (TASK-009; verified present in the current `project.pbxproj`). Since TASK-010 the only `PBXTargetDependency` entries in the project are the two UI-test bundles pointing at their tested apps (`MomoUITests` → `Momo`, `MomoWatchUITests` → `MomoWatch`) — the standard XCUITest shape, which links no app target to another. D-R3's "no target dependency" clause is satisfied **by construction**, not by convention.
2. **Companion relation declared, not structural.** `Apps/MomoWatch/Info.plist` carries `WKCompanionAppBundleIdentifier = com.momo.app`, pre-declaring the iPhone-companion pairing relation that EPIC-008's WatchConnectivity work needs — at the Info.plist level, with no build-time dependency created.
3. **Consistency with the deployment policy (ADR-006/ADR-008).** The standalone watch target carries ADR-008's pins — `WATCHOS_DEPLOYMENT_TARGET = 26.0`, `TARGETED_DEVICE_FAMILY = 4`, `SWIFT_VERSION = 6.0` (verified in the current pbxproj in both configurations). This ADR fixes project *shape* only; deployment numbers remain owned by ADR-006/ADR-008, and the current-generation pairing posture (ADR-008 Decision 3) is unaffected by the target being standalone.
4. **Concrete pins recorded at TASK-009** (cross-references, not re-derivations; the authoritative record is `.claude/tasks/completed/TASK-009-package-app-targets.md`, Implementation Notes, authenticated by REVIEW-TASK-009):
   - **Bundle IDs**: `com.momo.app` (iOS) / `com.momo.app.watchkitapp` (watchOS, companion-prefix convention) — chosen at TASK-009 (no value pre-recorded in any doc); **E4 name clearance remains the TASK-050 release gate** (REVIEW-TASK-009: bundle IDs are "sanity-checked only").
   - **tools-version 6.2** — the adversarially verified minimum manifest API for the `.v26` pins (REVIEW-TASK-009's tools-6.0 downgrade probe reproduced the `'v26' was introduced in PackageDescription 6.2` error).
   - **Hand-authored, committed pbxproj** (`Momo.xcodeproj`, objectVersion 56) — xcodegen is absent from the build machine; the committed text-diffable project builds from a fresh clone with zero setup. A build-tooling decision, recorded alongside because it produced the artifact this ADR governs.
   - `.macOS(.v26)` in the package manifest is host-only (`swift test` hosting) — no macOS product or target exists (REVIEW-TASK-009 proved this: no macOS product, no `MACOSX_DEPLOYMENT_TARGET` anywhere).
5. **Verified standalone.** The watch target builds and launches independently on the pinned simulator (Apple Watch SE 3 (40mm), watchOS 26.5) with its own bundle ID — TASK-009's verification evidence, re-run independently by REVIEW-TASK-009 with fresh PIDs and liveness checks. Independent buildability is a working consequence of the shape, exercised every development cycle since.
6. **Escape hatch, deliberately narrow.** If a later decision wants an embedded watch app inside the iOS product, TASK-009's record already classifies it as a deliberate follow-up superseding this ADR — not an incidental relapse.

## Alternatives Considered
- **Embedded watch app inside the iOS product** (the watch app as a nested target of the iOS app build, the pre-`WKApplication`-era packaging): rejected — it implies a `Momo` → `MomoWatch` target dependency, violating D-R3's enforcement clause literally, and nothing in the product requires it (MomoWatch owns a full independent role set per 05 §2.1 and its own bundle identity). TASK-009 recorded the flip as a deliberate follow-up if ever wanted. (TASK-009 Implementation Notes, "D-R3 standalone-watch decision"; REVIEW-TASK-009 Review Method item 10.)
- **Generated project via xcodegen** (committed `project.yml`, generated pbxproj): rejected for the project-authoring mechanism at TASK-009 — `which xcodegen` returns not-found on the build machine, and the task Context explicitly allowed the hand-authored fallback. The generate-don't-commit pattern was additionally rejected because a generated project is missing from fresh clones. Build tooling only — D-R6's zero-third-party rule governs app code, not build tooling. (TASK-009 Implementation Notes, "Build-tooling choice".)
- **Single-target monolith / multiple Xcode framework targets**: not re-weighed at TASK-009 — already adjudicated at ADR-005 (single app target with folder groups rejected: no machine-enforced purity boundary, no headless engine tests; multiple Xcode framework targets rejected: heavier configuration for the same result; SPM is the current-native mechanism). Cited here for completeness: this ADR sits on ADR-005's packaging as given. (ADR-005 Alternatives Considered; 05 §2.3 rationale paragraph.)

## Consequences
**What this binds for EPIC-008 (Watch App & Sync, delivery plan §3, TASK-040…044):**
- **The sync design inherits the packaging.** The Watch-side WC session lives in the `MomoWatch` app target and the iPhone-side session in the `Momo` app target (05 §2.1 target table; ADR-005's standing consequence that WC wrapper code is deliberately duplicated per app target — plain over DRY, with the testable journal/watermark logic in MomoKit). TASK-040 (iPhone-side session) and TASK-041/042 (glance + pat, Watch-side session) implement inside these targets; introducing a shared WC wrapper target would require superseding ADR-005/ADR-013.
- **The companion relation is already declared.** `WKCompanionAppBundleIdentifier` exists at the Info.plist level, so EPIC-008's paired-link work starts from a declared relation and adds **no target dependencies**.
- **What this ADR does NOT pre-decide**: EPIC-008's session/wrapper design details; the WC transport behaviors (VERIFY-AT-BUILD per ADR-003's recorded obligations and the 05 Appendix B register — TASK-040 resolves and records them); and the W1 UI (UX §6; TASK-041–043). ADR-003 already fixed the transport strategy (context latest-wins down, `transferUserInfo` journal up); this ADR fixes only *where the code lives*.
- **E4 name clearance (TASK-050) still applies to the recorded bundle IDs.** `com.momo.app` / `com.momo.app.watchkitapp` are pins-until-clearance; a clearance-driven rename is a build-setting change across both targets plus the companion-declaration line, not a packaging change.

**Standing risks and obligations:**
- **R9 (delivery plan §7 Risk Register; status.md Known Issues)** stands unchanged: paired Watch hardware is needed for the WC delivery obligations (TASK-044's device session is the explicit deliverable; simulators carry development). Standalone packaging does not alter this — it only means the watch app builds/installs/launches independently of the iPhone app during development, which is exactly how TASK-009/TASK-010 exercised it.
- **D-R3 stays a review check** on every future pbxproj change: no app-to-app target dependency. The current tree satisfies it (both app targets `dependencies = ()`; the only `PBXTargetDependency` entries are the UI-test bundles → their tested apps).
- An embedded-watch-app flip later is a distribution-shape change (App Store packaging implications) and would require a superseding ADR — per TASK-009's recorded follow-up note, never an incidental relapse.
