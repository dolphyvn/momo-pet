# ADR-004 — Pet State Engine: Pure Deterministic Core with Event-Driven Catch-Up

## Status
PROPOSED — under review (TASK-006). Becomes ACCEPTED upon REVIEW-TASK-006 approval. Implements project.md §23 and the TASK-005 §9 contract (normative intake).

## Context
Momo's behaviour is a real domain engine (§23): deterministic where tests require, with controlled injectable randomness (§8). The PRD owns the product numbers (§3 scales/bands/caps, §4 response matrix, §5 quests); 04 §9 owns the engine↔character interface (ResponsePlan, CharacterReport, handshakes, pause authority); TASK-006 owns the engine's internal design. Constraints: no background work beyond sync delivery (NFR-2), D18 state-gated-never-limit-gated semantics, D3/D4 no-punishment dynamics, D20 UTC instants with calendar-derived days, and FR-12's tone constraints binding on anything the engine emits.

## Decision
**A pure, timer-free, single-entry-point core.**
- `reduce(state, event, clock, rng) -> outcome` — one pure function in `MomoCore` (Foundation-only, Sendable value types, no I/O, no singletons). Clock and RNG are injected; identical inputs ⇒ identical outcome (FR-13 AC-3), property-tested.
- **Event-driven catch-up instead of ticks:** no engine timer, no polling, no background task. Elapsed time folds deterministically into segments (waking/night/midnight/nap) at each evaluation trigger — foreground open, any interaction, character report, scheduled in-session boundary (22:00 / 07:00 / midnight / nap-end), OS time-change notifications. A 7-day absence folds in microseconds; NFR-2 holds by construction.
- **Handshakes per 04 §9.2:** settle/wake/play are token-matched, idempotent for late/duplicate reports, and always paired with the `handshakeCancelled(HandshakeKind)` preemption path so no intermediate `wakefulness` can strand. **Play effects apply at the single instant the round ceases** — completion or cancellation — confirming 04 §9.6 item 4. **Interactions during settling decline warm, never queue**; interactions during waking also decline warm, the decline referencing the post-wake state (confirming both halves of 04 §9.6 item 8).
- **Bond by ledger:** enumerated per-day award events (hello +8 first-touch-either-device-never-window-gated; quests +4; variety +6; cap clamp-at-award +20) make FR-10 AC-1 true by construction; bond is monotonic everywhere (D3).
- **Quests generated by construction:** constraint filtering before the seeded draw (consecutive-pair ban; Q6-in-3-day-window with unknown-priors-forces-Q6); candidate space provably non-empty; the 30-day simulation is a sanity test, not the proof (FR-15 AC-2).
- **Day-stable seeds:** SHA-256(petID ‖ localDayKey ‖ epoch ‖ salt) → 64-bit seed; salts for choreography/copy/quest (04 §9.4 contract). Repo-owned SplitMix64-class generator; no system randomness in the core or sequencer.
- **Copy discipline at the type level:** the engine emits only catalog keys from the three approved namespaces — it composes no sentences, so guilt copy is structurally impossible; a static banned-vocabulary test backs the curation (FR-12).
- **Satiety window: 90 minutes** — the window VALUE is PRD-delegated; the response classes themselves are PRD-owned. Phases: 0–30 min `.full` (politely-full refusal, zero effects), 30–90 min `.recentlyFed` (nibble, ×0.25 — **this document's proposed third response class, flagged I-2 / OPEN-5 for owner confirmation**, since FR-6's letter assigns politely-full with zero effects to all of 0–90), then `.hungry`. Never gates availability (D18). Engine-owned starting value.
- **Counting rules (PRD letter):** feed counts always (FR-6 AC-3 — including refusals; flagged interpretation I-1 for review, required for Q3's ≤ 2-min completability); play counts on round completion only (FR-7 AC-2); pats always; care when performed.

Full spec: 05-technical-architecture §4 (state shape, fold rules, wakefulness machine, starting-value table, DisplayState derivation).

## Alternatives Considered
- **Continuous background ticking** (timer/`Task` loop advancing the pet): rejected — battery cost (NFR-2), suspend/terminate fragility (§32), and zero product value over catch-up folding, which produces identical state.
- **Reactive/stateful engine object** (@Observable engine mutating in place): rejected — breaks purity, determinism testing, and the value-type immutability requirement; the observable facade belongs to the app layer.
- **Watch-hosted engine or split evaluation:** rejected — two authoritative dynamic systems would need real conflict resolution (D5 dissolved instead by iPhone-only evaluation).
- **Queueing interactions during settling:** rejected in favor of decline-warm — hidden deferred execution surprises the user and adds a pending-intent machine for no product value (§4.7).

## Consequences
- Determinism, injectability, and headless macOS testing are structural, not aspirational; engine behavior for §32's entire edge matrix is simulatable without devices.
- Absence, night, and clock changes are warm by construction: drift targets are calm attractors; resets are dayKey-keyed and once-only; no code path can manufacture distress or guilt (D3/D4, INV-6 posture).
- The engine stays reusable for Phase 2 surfaces (widgets, notifications, HealthKit inputs) unchanged — they are new events/ports, not a redesign.
- Starting-value tunables (decline rates, attractor τ, effect sizes, satiety window value, repetition curve) are engine-owned constants documented in one table — tunable without PRD change, but only via review, each traced to its PRD direction; the response-class split within the satiety window is PRD-owned (I-2/OPEN-5 pending owner confirmation).
