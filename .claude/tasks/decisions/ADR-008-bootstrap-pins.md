# ADR-008 — Bootstrap Pins: Deployment Targets, Device Matrix, Test Framework

## Status
ACCEPTED — bootstrap facts recorded from the build machine's verified toolchain (TASK-008, fresh agent, 2026-09-08). Implements the ADR-006 policy ("pin minimum deployment targets at EPIC-002 bootstrap to the current stable shipping OS generation; N-1 re-evaluated at release") and resolves OPEN-3 and TR10 (05 Appendix B). Replaces 05 §2.4's and §12's "expected … VERIFY-AT-BUILD" placeholders with recorded evidence — including 05 §12's "expected 4.7\" SE-class" smallest-iPhone expectation, which the recorded evidence **confirms**: the smallest supported device is the iPhone SE (3rd generation) (see Decision 4).

The machine has since been provisioned (Xcode installed, developer directory selected, first launch completed, iOS + watchOS simulator runtimes downloaded); this ADR's numbers were re-verified from scratch by a fresh agent on 2026-09-08. The current shipping OS generation visible to this toolchain is therefore **generation 26** (iOS 26.x / watchOS 26.x).

## Decision
1. **Minimum iOS deployment target: iOS 26.0.** The toolchain's shipping generation is 26 (26.5 SDK shipped in Xcode 26.6); the pin is the generation floor, matching ADR-006's generation-level policy ("expected iOS 26 / watchOS 26 or their then-current successors").
2. **Minimum watchOS deployment target: watchOS 26.0.** Same generation evidence (watchOS 26.5 SDK; watchOS 26.5 runtime).
3. **iOS↔watchOS pairing rule:** a supported pair is (iPhone running iOS ≥ 26.0) + (paired Watch running watchOS ≥ 26.0) — **both floors ≥ 26.0, the current-generation floor (generation 26)**; within Phase 1 that makes every supported pair same-generation. Cross-generation pairs (either device on generation 25) are unsupported in Phase 1. Apple's system-level pairing rules are the enforcement boundary; Momo adds no app-side version gate. The formal pairing matrix is re-checked only if N-1 widening is approved at TASK-050 (ADR-006's gate).
4. **Device matrix (05 §12 shape; concrete names from `xcrun simctl list devices available` plus explicit SE-class device-type/runtime boot probes — the default list holds only current-generation devices and is not the set the pinned runtime supports, see the note below and the task file's fix pass; smallest member of each family governs its layout obligation):**
   - **iPhone small — governs FR-2 AC-1a no-scroll at default Dynamic Type: `iPhone SE (3rd generation)`** — the smallest device the pinned iOS 26 generation runs in this toolchain (native screenshot 750×1334 px = 375×667 pt, fix-pass probe in the task file; the next-smallest measured device, iPhone 17e, is 1170×2532 px = 390×844 pt).
   - **iPhone mid: `iPhone 17`** (1206×2622 px).
   - **iPhone large/flagship: `iPhone 17 Pro Max`** (1320×2868 px).
   - **Watch small — governs the ADR-001 glyph-legibility threshold (~32 pt): `Apple Watch SE 3 (40mm)`** — smallest visible watch (324×394 px). Apple Watch SE (2nd generation) 40mm also boots the pinned watchOS 26.5 runtime at the identical 324×394 px geometry (fix-pass probe, task file), so the ADR-001 ~32 pt threshold is stable across the supported SE-class watches — the choice of SE 3 (40mm) as matrix member is explicit, not coincidental.
   - **Watch flagship: `Apple Watch Series 11 (46mm)`** (416×496 px). `Apple Watch Ultra 3 (49mm)` (422×514 px) is the largest observed device and is the optional upper bound should a third watch point ever be needed.
   - Pixel dimensions were measured by booting each named simulator and reading `sips` pixelWidth/pixelHeight of a full-screen screenshot (evidence in the task file). 05 §12's "expected 4.7\" SE-class" smallest-iPhone expectation is **confirmed by this evidence**: the smallest device run by the pinned iOS 26 generation in this toolchain is the iPhone SE (3rd generation) at 750×1334 px (375×667 pt) — the default auto-created simulator list (`xcrun simctl list devices available`) shows only current-generation devices and is not the set of devices the pinned runtime supports; SE-class devices must be created explicitly (`simctl create` with the device-type/runtime pair) and boot the pinned iOS 26.5 runtime (fix-pass probe, task file). Physical screen diagonals are deliberately not asserted (§25); the 05 §12 budgets are measured on these named devices at TASK-045 regardless.
5. **Test framework: Swift Testing** for unit/property tests — verified present in this toolchain: a scratch SwiftPM package **outside the repo** compiled `import Testing` + `#expect`, and `swift test --list-tests` listed the test, exit 0 (verbatim output in the task file). UI automation remains **XCUITest (XCTest-based)** per 05 §10.6. Both are toolchain-native; zero third-party test dependencies (D-R4). TASK-009/TASK-010 wire the frameworks into the project's test targets and re-confirm in-target (their ownership per delivery plan §9).
6. **N-1 widening is DEFERRED, not decided here** — re-evaluated once at release planning (**TASK-050**) per ADR-006. (ADR-006's and 05 §2.4's text says "TASK-007" — pre-delivery-plan numbering; the backlog of record, delivery plan §3 EPIC-009 / §7 R13, owns the re-evaluation as TASK-050.) Until then, current-generation-only is the support posture, and no availability shims or `#if` back-deployment branches are expected.

## Alternatives Considered
- **Pin the exact toolchain point versions (iOS 26.5 / watchOS 26.5):** rejected — it would exclude in-generation users on earlier point releases for zero build simplification (no Phase 1 capability is point-release-gated); ADR-006's policy is generation-level, not point-release-level.
- **Pin N-1 now (iOS 25 / watchOS 25):** rejected for ADR-006's recorded reasons (no Phase 1 capability requires it; it expands the pairing matrix; it invites availability shims the product does not need) — explicitly preserved as the TASK-050 release option.
- **Defer the pins again:** rejected — TASK-009 needs concrete targets to create the package and app targets; further deferral strands the whole build DAG (delivery plan §4.1, risk R1).
- **XCTest for unit tests:** rejected — Swift Testing's availability is now verified evidence, resolving the framework side of 05 §10's "Swift Testing (current-native — VERIFY-AT-BUILD)"; XCTest survives only as the XCUITest UI automation substrate.
- **Apple Watch Ultra 3 (49mm) as the matrix flagship:** viable; Series 11 (46mm) chosen as the mainstream flagship matching 05 §12's "SE-class + flagship" contrast. Affects no governing obligation — the 40mm SE governs glyph legibility either way.
- **Support current-generation hardware only (drop SE-class devices from the matrix):** rejected at bootstrap — this is a product-scope decision (which hardware generations Momo supports at launch) reserved to the owner (CLAUDE.md §36), not a toolchain measurement; and it would **loosen** FR-2 AC-1a's and 05 §12's smallest-device obligations (a 375×667 pt viewport instead of the recorded smallest supported one). The iPhone SE (3rd generation) demonstrably boots the pinned iOS 26 runtime, so excluding SE-class hardware must be an explicit owner decision, not a supersession "from recorded evidence". Preserved as an available owner lever, not taken.

## Consequences
- TASK-009 consumes: min iOS 26.0, min watchOS 26.0, build SDKs 26.5, and the **five named matrix devices** (3 iPhone + 2 Watch) for simulator runs; `Apple Watch Ultra 3 (49mm)` remains the optional upper bound should a third watch point ever be needed.
- FR-2 AC-1a's no-scroll budget is verified against the **iPhone SE (3rd generation) simulator**; the ADR-001 ~32 pt glyph floor is verified against the **Apple Watch SE 3 (40mm) simulator**.
- "Smallest supported device" now has a recorded referent for every 05 §12 budget (launch, energy, memory measured on iPhone SE (3rd generation) / Apple Watch SE 3 (40mm) at TASK-045).
- Remaining VERIFY-AT-BUILD items are untouched by this ADR and keep their owning tasks (delivery plan §9): `swift test` hostability + in-target framework wiring (009/010), Swift `Clock` idioms (014), export tooling (025), WatchConnectivity behaviors (040/044), watchOS memory norms (045), required-reason APIs (048); Phase 2 items (§7–§9) stay reservations.
- If the build machine's Xcode is later replaced by a newer generation, these pins do not auto-update: re-pinning is a new ADR (bootstrap facts are recorded, not inferred).
- TR10 ("Xcode availability never verified") is retired as **verified**; delivery-plan risk R1 is mitigated. (status.md and docs/ are updated by the orchestrator, not by this task.)
